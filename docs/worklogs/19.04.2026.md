# Gunluk Calisma Ozeti

Bu belge, `19 Nisan 2026` tarihindeki AWS gecis oturumunda hangi adimlarin atildigini, hangi sorunlarla karsilasildigini ve nasil cozuldugunu kayit altina alir.

## Oturumun Amaci

Bugunku hedef, yerelde calisan proje iskeletini AWS tarafina tasimaya baslamakti. Bunun icin once AWS erisimi dogrulandi, sonra gercek bulut kaynaklari olusturuldu ve son olarak bu surec raporlanabilir hale getirildi.

## 1. Mevcut Durum Dogrulandi

- `tests.test_processor`

- `tests.test_dashboard_view_models`

Bunun anlami:

## 4. Config Katmanlari Lambda Uyumlu Hale Getirildi

`processor/config.py`, `api/config.py` ve `dashboard/config.py` dosyalarinda kucuk ama onemli bir iyilestirme yapildi. `python-dotenv` kutuphanesi olmasa bile konfig yuklemesi patlamayacak sekilde fallback mantigi eklendi.

Bu neden onemliydi:

- lokal gelistirmede `.env` dosyasi kullanabiliyoruz
- ama Lambda paketine her zaman ayni yardimci paketleri koymak istemeyebiliriz
- bu degisiklik, AWS paketlemesini daha hafif ve daha sorunsuz hale getiriyor

## 5. AWS CLI Eksigi Tespit Edildi ve Cozuldu

AWS tarafina gecmeye baslayinca ilk engel `aws` komutunun makinede bulunamamasi oldu.

Tespit edilen durum:

Bu nedenle `Amazon.AWSCLI` kuruldu. Kurulum sonrasi CLI su surumle hazir hale geldi:

- `aws-cli/2.34.32`

Bu adimdan sonra terminal tarafindan AWS ile konusmak teknik olarak mumkun hale geldi.

## 6. Access Key Yerine SSO Kullanilmasi Gerektigi Netlestirildi

Kullanicinin AWS Console ekranindaki kimlik tipi incelendiginde bunun klasik `IAM user` degil, `Federated user` oldugu goruldu. Bu bilgiye dayanarak `aws configure` ile sabit access key tanimlamanin dogru yol olmadigi sonucuna varildi.

Dogru cozum olarak:

- `aws configure sso`
- `aws sso login`

kullanildi.

Bu karar neden onemliydi:

- daha guvenli bir kimlik dogrulama modeli kullanildi
- root veya kalici access key kullanmaktan kacinildi
- kullanicinin mevcut AWS erisim bicimi ile uyumlu bir cozum secildi

## 7. SSO Kurulumunda Karsilasilan Sorunlar

SSO konfigurasyonu sirasinda birkac dogal ama onemli hata ile karsilasildi:

### Yanlis Start URL Kullanimi

Ilk denemelerde su tip URL'ler kullanildi:

- `signin.aws.amazon.com/console` baglantisi

Bu URL'ler `SSO start URL` olmadigi icin `Invalid start url provided` hatasi alindi.

### Dogru Yontemin Bulunmasi

Daha sonra AWS IAM Identity Center mantigi aciklandi ve aslinda gereken bilginin `AWS access portal URL` veya `Issuer URL` oldugu netlestirildi.

Sonunda kullanici su bilgilerle basarili bir SSO profile olusturdu:

- SSO session name: `ego-bus`
- SSO region: `us-east-1`
- Default client region: `eu-central-1`
- Profile name: `eemrezcan`

## 11. Lambda Execution Role Olusturuldu

AWS tarafinda bir sonraki adim olarak `ego-bus-lambda-role` isimli execution role olusturuldu. Bu role'a CloudWatch Logs, Kinesis ve DynamoDB izinlerini veren inline policy baglandi.

Bu asama onemliydi cunku Lambda'nin:

- log yazabilmesi
- Kinesis kayitlarini okuyabilmesi
- DynamoDB'ye yazabilmesi

ancak dogru IAM izinleri ile mumkundu.

## 12. Lambda Paketleme ve Deploy Yapildi

`processor` kodu Lambda uyumlu zip paketi haline getirildi ve `ego-bus-processor` isimli function olarak `eu-central-1` bolgesine deploy edildi.

Function konfigurasyonu:

- runtime: `python3.12`
- handler: `processor.lambda_handler.lambda_handler`
- memory: `256 MB`
- timeout: `30 saniye`

Bu asamada iki teknik problem goruldu ve cozuldu:

### Rezerve Environment Variable Problemi

Ilk deploy denemesinde `AWS_REGION` degiskeni elle set edilmeye calisildi. Lambda bu alani rezerve ettigi icin deploy reddedildi. Sonrasinda script guncellenerek bu alan kaldirildi.

### Eksik Modul Problemi

Ilk invoke denemesinde `No module named 'simulator'` hatasi alindi. Bunun nedeni Lambda paketine `simulator/` klasorunun dahil edilmemesiydi. Paketleme script'i duzeltilerek bu klasor de zip icine eklendi ve problem giderildi.

## 13. Event Source Mapping Kuruldu

`ego-bus-telemetry-stream` ile `ego-bus-processor` arasinda event source mapping olusturuldu. Bu sayede stream'e dusen telemetri kayitlari Lambda tarafina otomatik aktarilmaya basladi.

Olusan mapping icin son durum:

- state: `Enabled`
- last processing result: `OK`

## 14. Kinesis Uzerinden Ilk Gercek Uctan Uca Dogrulama Yapildi

Lambda tek basina once dogrudan invoke edilerek test edildi. Gecerli bir payload ile calistigi ve `bus_current_state` tablosuna yazabildigi goruldu.

Ardindan Kinesis stream uzerine gecerli bir telemetri kaydi yazildi. Bir sure sonra ayni `bus_id` icin DynamoDB tablosunda kayit goruldu. Bu, asagidaki zincirin gercek AWS uzerinde calistigini kanitladi:

`Kinesis -> Lambda -> DynamoDB`

Ozellikle `BUS_520_03` icin girilen ornek kaydin tablodaki sonucunda su alanlar goruldu:

- `estimated_eta_sec`
- `estimated_alighting_count`
- `estimated_occupancy_score`
- `estimated_occupancy_level`
- `is_delayed`

Bu da bulutta hesaplanan alanlarin yalnizca yerelde degil, AWS ortami icinde de gercekten calistigini gostermistir.

## 15. Batch Hata Dayanikliligi Iyilestirildi

Ilk Kinesis testlerinde gecersiz `bus_id` degerleri kullanildigi icin Lambda batch bazli hata veriyordu. Bu durum shard uzerindeki akisi gereksiz yere kilitleme riski olusturuyordu.

Bu nedenle `lambda_handler` guncellendi:

- gecersiz payload'lar loglaniyor
- ama tum batch dusurulmuyor
- gecerli payload'lar islenmeye devam ediyor

Bu iyilestirme, gercek veri akisinda tek bir bozuk kaydin tum akis hattini durdurmamasi icin onemliydi.

## 17. IoT Core Uzerinden Ilk Bulut Testi Yapildi

IoT topic rule dogrudan test edildi. AWS CLI ile IoT data endpoint'ine ornek bir telemetri mesaji publish edildi. Bir sure sonra `bus_current_state` tablosunda `BUS_520_04` kaydi goruldu.

Bu, IoT Core'dan gelen verinin Kinesis'e aktarildigini, Lambda tarafinda islendigini ve sonunda DynamoDB'ye yazildigini dogruladi.

## 18. Gercek Simulator Ile AWS IoT Core Testi Yapildi

Bir sonraki asamada simulator dogrudan AWS IoT Core endpoint'ine baglanacak sekilde calistirildi. Baslangicta publish cagrisi `QoS 0` ile gonderildigi icin uzak broker tarafinda mesajlar istemci kapanmadan once tam iletilmeyebiliyordu.

Bu nedenle `simulator/publisher.py` guncellendi:

- MQTT publish `QoS 1` ile gonderildi
- `wait_for_publish()` ile yayin tamamlanmadan istemci kapatilmaz hale getirildi

Bu iyilestirme sonrasinda simulator tekrar AWS IoT Core'a baglandi ve `BUS_510_01` icin veri `bus_current_state` tablosunda goruldu.

Bu an, hedeflenen mimarinin en guclu kanitidir:

`Simulator -> AWS IoT Core -> Kinesis -> Lambda -> DynamoDB`

## 19. FastAPI Katmani AWS Verisi Ile Dogrulandi

AWS tarafinda veri akisi ve yazma katmani calisir hale geldikten sonra okuma katmani da test edildi. Bunun icin API tarafina `AWS_PROFILE` destegi eklendi ve `ApiSettings` ile `DynamoDbReadRepository` yapisi kullanilarak servis katmani dogrudan gercek AWS verisi uzerinde calistirildi.

Sonrasinda FastAPI uygulamasi kisa sureli olarak `dynamodb` modunda ayaga kaldirildi ve su endpoint'ler test edildi:

- `/health`
- `/summary`
- `/buses`

Bu endpoint'lerin hepsi beklenen sekilde cevap verdi. Donen cevaplarda `bus_current_state` tablosundaki gercek kayitlar, line name ve turetilmis alanlarla birlikte goruldu.

Bu asama, buluttaki verinin yalnizca saklandigini degil, ayni zamanda API katmani uzerinden tuke tilebildigini de kanitladi.

## 20. Dashboard AWS Verisi Ile Acildi

Bir sonraki adimda Streamlit dashboard gercek AWS verisine bagli API uzerinden calistirildi. Bunun icin:

- FastAPI `dynamodb` modunda ayaga kaldirildi
- `DASHBOARD_API_BASE_URL` bu API'ye yonlendirildi
- Streamlit dashboard headless modda baslatildi

Dogrulama sonucunda:

- API `/health` endpoint'i `storage_mode=dynamodb` ile cevap verdi
- API `/summary` endpoint'i gercek AWS verisini dondu
- dashboard sunucusu HTTP `200` ile acildi

Bu adim, sistemin son kullaniciya gosterilen gorsel katmaninin da gercek bulut verisiyle calistigini gostermektedir.
